\begin{abstract}
Future Internet architectures demand programmable network exposure
frameworks that can bridge high-level operator intents to concrete
telecom API invocations without manual payload composition.
This paper presents the design, implementation, and empirical evaluation
of a cloud-native, intent-based telco orchestration platform combining
3GPP Common API Framework (CAPIF) integration, CAMARA-aligned service
semantics, NEF-backed telecom realisation, and large language model
(LLM)-assisted planning.
The system is implemented as a multi-container FastAPI control plane with
a product-style operator interface, live CAPIF invoker onboarding and
service discovery, provider publication, persistent NEF data services,
and a three-layer deterministic validator that guards all LLM-generated
API payloads before execution.
Both deterministic and LLM-assisted planning modes are supported;
the latter grounded in runtime CAMARA OpenAPI schema injection
(schema-grounded prompting) rather than vector-based retrieval.
Empirical evaluation on a 60-entry bilingual (English/Turkish)
ground-truth dataset using six formally defined reliability metrics
yields: IWSR\,=\,100\,\% (deterministic) and IWSR\,=\,95\,\%
(LLM-assisted, Claude Haiku\,4.5), with perfect Schema Compliance
(SCR\,=\,100\,\%) and Semantic Validity (SVR\,=\,100\,\%) in both modes
and a Stability Score of SS\,=\,0.938 across repeated LLM runs.
All LLM failures are service-routing errors on deliberately ambiguous
intents; no payload schema violation occurs in either mode.
The platform and dataset are publicly available as open-source artefacts,
providing a reproducible research baseline for intent-based orchestration
in 5G and beyond-5G service exposure environments.
\end{abstract}

\section{Introduction}
% =============================================================================

The emergence of Beyond-5G (B5G) and 6G network architectures elevates
programmable service exposure from an optional feature to a foundational
design principle of the Future Internet.
Standardised frameworks such as 3GPP CAPIF (TS\,23.222)~\cite{3gpp_capif}
and the Linux Foundation CAMARA project~\cite{camara2022} define the
governance, discovery, and semantic layers that enable vertical industries
and developers to consume network capabilities through well-defined APIs.
At the same time, NEF-based provider stacks~\cite{nefsim2022} bridge those
developer-facing interfaces to the underlying telecom data plane,
resolving identifiers, enforcing policies, and returning structured
monitoring results.

This two-tier model --- CAPIF/CAMARA for exposure governance and
NEF for realisation --- creates an environment in which sophisticated
orchestration logic is required: requests arrive as natural language
intents from operators or automated management planes, and must be
translated into precisely structured, multi-field API payloads
complying with strict telecom domain constraints (E.164 phone formats,
enumerated QoS profiles, duration bounds, CAPIF registry membership).
Manual composition at this level is error-prone and scales poorly,
motivating automated intent-to-API translation.

Large language models (LLMs) offer a compelling approach:
their instruction-following capabilities can, in principle,
translate free-text intents into structured API calls without
explicit rule encoding~\cite{maatouk2025,flowmind2023}.
However, telecom API payloads impose hard correctness constraints
that probabilistic generation cannot guarantee without external
enforcement~\cite{liu2024,telagentbench2025}.
Hallucinated service identifiers, malformed phone numbers,
or invalid QoS profile names would silently propagate to production
networks if not intercepted.

This paper addresses the gap between LLM planning capability and
telecom-grade reliability through a platform that:
(i)~combines live CAPIF governance with multi-provider LLM planning;
(ii)~enforces correctness through a three-layer deterministic validator
(schema, semantic policy, and CAPIF registry);
(iii)~provides a structured feedback correction loop for bounded
iterative repair; and
(iv)~is evaluated on a bilingual 60-entry ground-truth dataset using
six formally defined reliability metrics, yielding concrete,
reproducible performance figures.

Unlike conceptual architectures or simulation-only prototypes,
the system reported here is fully deployed as a multi-container
Docker stack, operates against live OpenCAPIF and live FRONT-research-group
CAMARA providers, and includes a public open-source release
of all code, datasets, and evaluation scripts.

The work reported here is grounded in three research questions:
\begin{enumerate}[leftmargin=1.5em,label=\textbf{RQ\arabic*.}]
  \item Can a schema-grounded two-phase LLM planner achieve telecom-grade
        payload correctness (SCR\,=\,SVR\,=\,100\%) without fine-tuning?
  \item What is the primary failure mode of LLM-driven intent-to-API
        translation in a CAPIF-constrained service exposure environment?
  \item Does a bilingual (English/Turkish) intent set reveal
        statistically significant cross-lingual reliability differences?
\end{enumerate}
The evaluation results answer all three questions empirically with
quantified, reproducible measurements on an open dataset.

\section{Related Work}
\label{sec:related}
% =============================================================================

\subsection{Intent-Based Networking and Orchestration}

Intent-based networking (IBN) has been explored extensively at the NFV
orchestration level. Rafiq et al.~\cite{rafiq2020} demonstrated
deterministic intent-to-descriptor translation across multiple
orchestrators; Saraiva de~Sousa et al.~\cite{saraiva2019} identified
intent abstraction as a key direction for adaptive service management;
and Coronado et al.~\cite{coronado2022} positioned intent-driven
closed-loop control as foundational to zero-touch 6G management.
These works operate at the orchestration lifecycle level and generally
assume structured intent inputs, not natural language.

\subsection{5G Network Exposure Infrastructure}

On the exposure infrastructure side, Molina~Sanchez et al.~\cite{molina2022}
implemented CAPIF Core Function as an open-source microservice (OpenCAPIF),
enabling community experimentation with 3GPP-compliant API exposure.
Fragkos et al.~\cite{nefsim2022} introduced NEFSim as an open NEF
experimentation platform covering the full 3GPP service exposure stack.
Turkovic et al.~\cite{turkovic2025} demonstrated 3GPP-compliant CAMARA
QoD and Location API integration in a real CAM testbed, measuring
end-to-end call-flow latency of 230--340\,ms.
Our work builds on these open platforms as provider components and
focuses on the intent translation and orchestration layer above them.

\subsection{LLMs for Telecom and Structured Output}

Maatouk et al.~\cite{maatouk2025} identified hallucination and output
inconsistency as primary risks for LLM deployment in telecom operations.
Liu et al.~\cite{liu2024} benchmarked structured-output compliance of
several leading LLMs and found that even GPT-4 achieves only an average
compliance score of 0.40 on JSON schema tasks.
Lee et al.~\cite{telagentbench2025} introduced TelAgentBench, confirming
that multi-turn planning tasks significantly degrade LLM pass rates in
telecom agent scenarios.
Zeng et al.~\cite{flowmind2023} demonstrated near-perfect workflow
generation accuracy when LLMs are grounded in structured API
descriptions --- the approach adopted in Phase\,2 of our planner.

\subsection{Research Gap}

To the best of our knowledge, no prior work provides end-to-end
empirical reliability evaluation of LLM-based natural-language
intent-to-API translation within a live CAPIF-compliant 5G service
exposure environment, operating under simultaneous schema, semantic, and
registry constraints, and reporting a standardised six-metric reliability
framework on a bilingual ground-truth dataset.

\section{System Objectives and Contributions}
\label{sec:contrib}
% =============================================================================

The platform was built with four primary objectives:

\begin{itemize}[leftmargin=1.1em]
  \item to unify CAPIF onboarding, discovery, and provider publication
        inside one operator-facing control plane,
  \item to expose CAMARA-aligned telecom capabilities through a live,
        guarded orchestration backend,
  \item to support both deterministic and LLM-assisted natural-language
        planning with explicit mode selection,
  \item to ensure that all execution paths remain guarded by deterministic
        validation and schema enforcement regardless of planning mode.
\end{itemize}

\noindent Its main contributions are:

\begin{itemize}[leftmargin=1.1em]
  \item a working, openly-released CAPIF-aware telco orchestration backend
        operating against live CAMARA providers,
  \item a pluggable multi-provider LLM planning layer (Gemini, OpenAI,
        Anthropic) grounded by runtime CAMARA OpenAPI schema injection
        and live CAPIF discovery,
  \item a three-layer deterministic validator (L1 Pydantic schema, L2
        telecom semantic policy, L3 CAPIF registry),
  \item a structured feedback correction loop for bounded iterative
        repair of invalid LLM-generated payloads,
  \item a bilingual 60-entry ground-truth evaluation dataset with
        difficulty stratification and multi-country phone number coverage,
  \item six formally defined reliability metrics (IWSR, SCR, SVR, HR,
        SS, RRF) constituting a reusable evaluation framework for
        intent-to-API orchestration systems.
\end{itemize}

  \item \textbf{backend} (FastAPI, port\,8000): orchestration control

  \item \textbf{OpenCAPIF Core Function}: 3GPP-compliant register,
        discovery, and security services.
  \item \textbf{NEF provider} (port\,8080): FRONT-research-group NEF

  \item \textbf{camara-QoD provider} (port\,8090): CAMARA

  \item \textbf{NEF-QoS provider} (port\,8585): 3GPP AsSessionWithQoS

\end{itemize}

All containers share a Docker bridge network; service discovery across
providers is handled at run time by the CAPIF client querying the Core
Function's discovery endpoint rather than by static configuration.
A named Docker volume persists MongoDB data across container restarts,
and an initialisation script (\texttt{mongo-init.js}) seeds location,
IMSI, and polygon records on first deployment.

The FRONT-research-group provider stacks are included as Git submodules,
enabling version-tracked integration while keeping the main repository
lightweight. Provider publication to CAPIF follows the standard APF
sequence: onboard provider identity, submit OpenAPI metadata,
and verify appearance in CAPIF discovery results.

\subsection{Software Quality and Test Coverage}

The platform includes 65 automated unit tests organised across three
pytest modules: \texttt{test\_intent\_engine.py} (keyword routing
coverage across all four services and edge cases),
\texttt{test\_validator.py} (L1/L2/L3 layer isolation tests,
including boundary conditions for E.164 format, duration bounds,
and QoS profile enumeration), and \texttt{test\_executor.py}
(orchestration flow tests in deterministic mode using fixture

Tests are designed to be runnable without any LLM API key or live
CAPIF connection, enabling CI/CD integration without external dependencies.
The test suite serves as a regression guard for validator rules,
ensuring that changes to schema definitions or semantic policy do not
silently degrade correctness across the evaluation dataset.

\subsection{Supported Telecom Capabilities}

The platform exposes four CAMARA-standardised orchestration targets:
\textit{Quality on Demand (QoD)} for temporary QoS session creation
(CAMARA QoD v1.1.0);
\textit{QoS Profiles} for available profile enumeration
(CAMARA QoS-Profiles v1.1.0);
\textit{QoS Provisioning} for long-lived QoS assignment via 3GPP
AsSessionWithQoS (CAMARA QoS-Provisioning v1.1.0, TS\,29.122); and
\textit{Location Retrieval} for device location access through
NEF-backed MonitoringEvent subscriptions
(CAMARA Location-Retrieval v0.5).

\subsection{Planning Modes}

\texttt{POST /orchestrate} accepts a \texttt{mode} field with three values.
\textit{Deterministic} mode applies keyword-based routing without any
LLM call, providing a reliable, cost-free baseline always available.
\textit{LLM-assisted} mode invokes the two-phase planner and fails
explicitly when the planning call returns an error, avoiding silent
degradation.
\textit{Auto} mode attempts LLM planning first and falls back to
deterministic mode on failure, enabling graceful degradation in
production.
This design keeps the AI layer optional while preserving full
functionality regardless of LLM availability.

\section{CAPIF Integration Workflow}
\label{sec:capif}
% =============================================================================

\subsection{CAPIF Roles and Governance Model}

CAPIF provides the exposure governance plane for the entire platform.
The backend acts as an \textbf{Invoker} consuming exposed APIs;
CAMARA and NEF providers act as \textbf{API Exposing Functions (AEFs)}
publishing service descriptions; and the OpenCAPIF stack provides the
\textbf{Core Function} managing discovery, authentication, and
onboarding~\cite{molina2022}.
This three-role model means that every API invocation is governed:
services are visible to the orchestration layer only after publication,
and the L3 validator can query the live registry to detect hallucinated
service identifiers.

\subsection{Invoker Onboarding Flow}

The onboarding implementation in \texttt{backend/capif/client.py}
follows the 3GPP CAPIF-2e reference point:
(1)~authenticate against the register service using pre-shared credentials;
(2)~generate an RSA private key and certificate signing request (CSR)
locally;
(3)~submit the onboarding request to the CAPIF Core Function;
(4)~receive an \texttt{apiInvokerId} and invoker certificate chain;
(5)~store runtime credentials for subsequent mTLS-authenticated discovery
and execution.
The platform therefore operates as a real CAPIF invoker rather than a
static mock client.
CAPIF serves three distinct orchestration functions:
\textbf{identity onboarding} (credential provisioning),
\textbf{service governance} (API visibility after publication), and
\textbf{discovery} (live registry queries at orchestration time).

\subsection{Discovery and Publication}

\texttt{GET /capif/discover} queries the CAPIF registry using the
invoker's mTLS certificate and returns live service descriptions,
including API names, endpoint URIs, and published security information.
This discovery output is optionally injected into the LLM's Phase\,1
prompt, grounding service selection in live registry state rather than
static configuration.
Provider publication follows the standard APF sequence:
onboard provider identity, submit OpenAPI metadata through the CAPIF-4
reference point, and verify appearance in subsequent discovery responses.

\section{CAMARA and NEF Service Realisation}
\label{sec:camara}
% =============================================================================

CAMARA defines the API-facing service contracts (the \emph{semantic layer}),
while CAPIF provides the exposure governance layer.
Provider services from the FRONT-research-group~\cite{turkovic2025}
bridge these interfaces to telecom behaviour.
The QoD provider handles temporary session creation via the CAMARA QoD
API, mapping requests to the underlying radio resource management plane.
The NEF Monitoring Event provider resolves phone numbers to IMSI
identifiers, reads location and polygon data from MongoDB, and returns a
3GPP-style monitoring result; the CamaraLocationRetrieval adapter then
normalises this into the CAMARA Location Retrieval format~\cite{nefsim2022}.

The Location Retrieval end-to-end execution path comprises six steps:
(1)~intent mapped to \texttt{location-retrieval} service;
(2)~provider constructs a 3GPP MonitoringEvent subscription request;
(3)~provider obtains a CAPIF security token;
(4)~NEF API is called with the subscription;
(5)~NEF resolves the IMSI, reads polygon data from MongoDB;
(6)~response normalised to CAMARA format and returned to the caller.

\section{LLM-Assisted Planning Layer}
\label{sec:llm}
% =============================================================================

\subsection{Schema-Grounded Two-Phase Planning}

\texttt{backend/llm\_planner.py} implements a two-phase pipeline
designed to separate service routing from payload generation,
limiting each LLM call to a well-scoped subtask with a clearly
defined schema target.

\textit{Phase\,1 — Service Selection:}
The LLM receives (a)~the user intent in natural language,
(b)~a schema-grounded summary of all CAMARA services and operations
extracted at startup by parsing YAML OpenAPI descriptors,
and (c)~optionally, live CAPIF discovery results.
It returns a JSON object specifying \texttt{service\_id},
\texttt{operation\_id}, \texttt{method}, \texttt{path}, and a
\texttt{rationale} field.
The rationale enables downstream traceability without additional
instrumentation.

\textit{Phase\,2 — Payload Generation:}
Given the Phase\,1 selection, the LLM receives the full CAMARA OpenAPI
schema for that specific operation, extracted by parsing the appropriate
YAML file at runtime.
It returns a complete, schema-aligned JSON payload matching the
operation's request body specification.
Grounding the payload prompt in the actual operation schema (rather than
a generic description) is the key mechanism achieving SCR\,=\,100\%
in LLM-assisted mode.

The planner proposes structured actions but never executes them directly;
all output passes through the three-layer validator before any provider
call is made.

\subsection{Multi-Provider LLM Dispatcher}

Three LLM providers are supported via a unified dispatcher interface:
Gemini (\texttt{GEMINI\_API\_KEY}), OpenAI (\texttt{OPENAI\_API\_KEY}),
and Anthropic (\texttt{ANTHROPIC\_API\_KEY}).
The dispatcher selects the active provider from environment configuration,
enabling provider substitution without code changes.
The full 60-entry evaluation in this paper used
\textbf{Claude Haiku\,4.5} (model: \texttt{claude-haiku-4-5-20251001},
temperature\,0.1) at a total API cost of approximately \$0.35 across
all evaluation and stability-score runs (300 total LLM call pairs),
demonstrating that empirical reliability measurement is accessible even
at very low budget.

\subsection{Structured Feedback Correction Loop}

When Phase\,2 output fails the three-layer validator, the feedback
engine constructs a structured correction prompt containing: the original
intent, the rejected payload JSON, and layer-tagged error messages
(e.g., \texttt{[L1] device.phoneNumber must match E.164}).
This prompt is submitted to the same LLM for regeneration.
The loop repeats up to \texttt{MAX\_ITERATIONS\,=\,3}, after which
the most recent attempt is returned with the validation error attached.
Recovery metadata is recorded in a \texttt{FeedbackMetadata} object
and included in the orchestration response, enabling offline analysis
of correction convergence rates.

\subsection{Representative Orchestration Example}

An LLM-assisted dry-run request with intent
``\textit{Boost video QoS for +905551112233 for 15\,minutes}'' produced:
service\,=\,\texttt{qod},
operation\,=\,\texttt{createSession},
path\,=\,\texttt{/quality-on-demand/v1/sessions},
duration\,=\,900\,s,
profile\,=\,\texttt{QOS\_E\_STREAMING}.
The three-layer validator confirmed structural, semantic, and registry
compliance in a single pass, and no feedback iteration was required.

\section{Reliability Evaluation Framework}
\label{sec:eval}
% =============================================================================

\subsection{Formal Metric Definitions}

Intent-to-API translation is formalised as a mapping
$f_\theta : \mathcal{I} \rightarrow \mathcal{W}$,
where $\mathcal{I}$ is the set of natural language intents and
$\mathcal{W}$ is the set of CAPIF-compliant API workflows generated
by LLM $f_\theta$ (or the deterministic engine in baseline mode).

\subsubsection{Intent-to-Workflow Success Rate (IWSR)}
\begin{equation}
\text{IWSR} = \frac{|\{w \in \mathcal{W} \mid w = w^*\}|}{|\mathcal{I}|}
\end{equation}
where $w^*$ is the ground-truth workflow.
IWSR is the primary end-to-end correctness metric: it requires
both correct service selection \emph{and} a valid, semantically
correct payload matching the ground truth.

\subsubsection{Schema Compliance Rate (SCR)}
\begin{equation}
\text{SCR} = \frac{|\{w \in \mathcal{W} \mid w \models \text{Schema}\}|}{|\mathcal{W}|}
\end{equation}
Fraction of generated payloads passing Layer\,1 (Pydantic) structural
validation, independent of semantic correctness.

\subsubsection{Semantic Validity Rate (SVR)}
\begin{equation}
\text{SVR} = \frac{|\{w \in \mathcal{W} \mid w \models \text{TelecomPolicy}\}|}{|\{w \in \mathcal{W} \mid w \models \text{Schema}\}|}
\end{equation}
Among schema-compliant payloads, the fraction that also pass Layer\,2
telecom domain policy checks: E.164 phone format, valid QoS profile
identifiers, duration bounds (1--7200\,s), IPv4 unicast address
validation, and operation/method consistency.

\subsubsection{Hallucination Rate (HR)}
\begin{equation}
\text{HR} = \frac{|\{w \in \mathcal{W} \mid w \not\subseteq \mathcal{A}_{\text{reg}}\}|}{|\mathcal{W}|}
\end{equation}
where $\mathcal{A}_{\text{reg}}$ is the set of APIs present in the
CAPIF live registry.
HR measures service-selection hallucinations: the LLM returns a
service identifier that does not exist in the registered catalog.

\subsubsection{Stability Score (SS)}
Given $k$ repeated runs of the same intent set, each producing a
workflow, with $d$ distinct output tuples observed across runs:
\begin{equation}
\text{SS} = 1 - \frac{d - 1}{k}
\end{equation}
Perfect stability ($d\,=\,1$, identical output every run) yields
$\text{SS}\,=\,1.0$.
SS is computed by running the 60-entry dataset $k\,=\,5$ times and
measuring output variance per entry averaged over all entries.

\subsubsection{Recovery Rate after Feedback (RRF)}
\begin{equation}
\text{RRF} = \frac{|\{w_c \mid w_i \not\models \text{Schema}
             \,\wedge\, w_c = w^*\}|}
             {|\{w_i \mid w_i \not\models \text{Schema}\}|}
\end{equation}
Among initially schema-invalid payloads, the fraction that the
feedback loop successfully corrects to a ground-truth-matching
workflow.
RRF is undefined (denominator\,=\,0) when SCR\,=\,100\%,
i.e., when no payload fails schema validation on the first attempt.

\subsection{Evaluation Dataset}

The ground-truth dataset (\texttt{datasets/ground\_truth.json}) contains
60 manually crafted entries spanning all four supported services:
20 for QoD Session creation, 15 for Location Retrieval,
10 for QoS Profile discovery, 10 for QoS Provisioning,
and 5 deliberate edge cases (ambiguous or boundary-condition intents).
Difficulty is stratified as: 24 easy, 20 medium, 16 hard.
Language coverage is 32 English and 28 Turkish entries,
providing bilingual robustness evaluation without additional prompt
engineering.
Phone numbers span four country codes (+30\,GR, +90\,TR, +34\,ES,
+1\,US) sourced from FRONT-research-group test fixtures,
testing E.164 format validation across international prefixes.

\subsection{Error Analysis}

The 5\,\% IWSR gap in LLM mode corresponds to 3 entries out of 60,
all classified as service-selection errors (HR\,=\,5\%):
the LLM selects a valid, registered service but the wrong one for
the given intent.
Two failure patterns were identified.

\textit{Pattern 1 — QoD vs.\ QoS Provisioning ambiguity (2 entries):}
Intents containing ``critical communications QoS'' or ``emergency QoS''
caused the model to select \texttt{qos-provisioning} (long-lived
permanent assignment) instead of \texttt{qod} (temporary session).
The model correctly identifies the QoS priority requirement but
misinterprets the temporal scope from the phrasing.

\textit{Pattern 2 — Edge case boundary (1 entry):}
An intent specifying a very short duration (``QoS for 30\,seconds'')
caused route confusion between a QoD temporary session and a
provisioning operation.
Explicit temporal quantifiers in the future prompt design would
address both patterns.

Critically, in all failure cases, the \emph{payload} generated for the
wrongly-selected service was structurally and semantically valid
(SCR\,=\,SVR\,=\,100\%), confirming that Phase\,2 schema grounding
fully prevents payload-level errors; the residual failure mode is
entirely in Phase\,1 service routing.

\section{Persistence and Three-Layer Validation}
% =============================================================================

\subsection{Persistent NEF Data}

The NEF stack stores location and polygon records in MongoDB.
A named Docker volume at \texttt{/data/db} prevents data loss across
container restarts, and an auto-seeding initialisation script at
\texttt{/docker-entrypoint-initdb.d/mongo-init.js} populates required
records on first deployment.
Subsequent restarts preserve the existing dataset without manual
reseeding, enabling reproducible evaluation across sessions.

\subsection{Three-Layer Validation Detail}

Execution never depends solely on LLM output.
All generated payloads pass three independent validation tiers
sequentially before any provider call is made:

\begin{itemize}[leftmargin=1.1em]
  \item \textbf{L1 — Schema (SCR):} Pydantic v2 model validation
        enforcing required fields, correct types, nested object
        structure, and field constraints (e.g., duration as positive
        integer).
        Failures produce structured error objects returned to the
        feedback engine.
  \item \textbf{L2 — Semantic Policy (SVR):} Eight domain-specific
        deterministic rules: E.164 phone number format
        (\texttt{\textasciicircum[+][1-9]\textbackslash d\{7,14\}\$}),
        valid QoS profile identifiers from the CAMARA enumeration,
        duration within \mbox{1--7200\,s}, IPv4 unicast address
        validation, operation/method consistency, and device field
        completeness.
  \item \textbf{L3 — CAPIF Registry (HR):} Live CAPIF discovery query
        to verify the selected \texttt{service\_id} exists in the
        published registry.
        This layer is non-blocking on CAPIF unavailability
        (fails open) but records the check result in the response
        for audit traceability.
\end{itemize}

This architectural separation between probabilistic LLM reasoning and
deterministic telecom constraint enforcement is the central property
enabling quantified reliability guarantees independent of LLM quality.

No prior work combines all five dimensions simultaneously.
The absence of live CAPIF integration in most LLM-for-telecom studies
means that hallucinated service identifiers (measured by HR) cannot even
be detected, let alone counted.
Our platform is unique in making all five properties co-present and
empirically evaluated.

\subsection{Insight: Schema Grounding Solves Payload Errors}

The most significant empirical finding is that schema-grounded Phase\,2
prompting eliminates payload-level LLM errors entirely (SCR\,=\,SVR\,=\,100\%).
This confirms the FlowMind hypothesis~\cite{flowmind2023} in a live
telecom environment: providing the exact operation schema as context is
sufficient for an instruction-following LLM to generate structurally and
semantically valid API payloads.
The remaining 5\,\% failure is a service-routing problem (Phase\,1),
which is a coarser-grained classification task amenable to improved
prompting, few-shot examples, or fine-tuning.

\subsection{Deterministic vs.\ LLM: Complementarity, Not Competition}

The deterministic mode achieves IWSR\,=\,100\% but requires explicit
keyword matching for every intent pattern, making it brittle to novel
phrasing and non-English inputs.
LLM-assisted mode achieves IWSR\,=\,95\% with zero implementation
cost per new intent pattern and robust cross-lingual coverage
(Turkish\,=\,96.4\%, English\,=\,93.8\%).
The \textit{auto} mode combining both --- LLM primary, deterministic
fallback --- offers the best practical trade-off: near-LLM flexibility
with deterministic reliability as a safety net.

\subsection{Cost and Scalability}

At \$0.35 for 300 two-phase LLM call pairs (60 entries $\times$ 5
stability runs), the per-intent cost is approximately \$0.0012 at
Claude Haiku\,4.5 pricing.
The three-layer validator adds sub-millisecond overhead, making it
negligible relative to network round-trips.
The platform's stateless control plane scales horizontally without
architectural changes; the main scalability bottleneck at higher loads
would be LLM API rate limits, addressable through request batching or
model serving infrastructure.

\subsection{Limitations}

The current evaluation has three notable limitations.
First, only one LLM (Claude Haiku\,4.5) is benchmarked; cross-model
comparison is deferred to future work.
Second, the 60-entry dataset, while bilingual and difficulty-stratified,
is manually crafted; ecological validity against real operator intent
logs remains unverified.
Third, execution is performed in \textit{dry-run} mode during
evaluation; end-to-end live execution success rates may differ from
IWSR due to transient provider or network errors not modelled in the
current framework.

\section{Conclusion}
\label{sec:conclusion}
% =============================================================================

This paper presented a cloud-native, AI-native telco orchestration
platform for intent-to-API planning in Future Internet service exposure
environments.
The system integrates 3GPP CAPIF governance, CAMARA service semantics,
NEF-backed telecom realisation, three-layer deterministic validation,
a structured feedback correction loop, and multi-provider LLM-assisted
planning into one deployable, open-source control plane.

Empirical evaluation on a bilingual 60-entry dataset using six formally
defined reliability metrics demonstrates that the combination of
schema-grounded two-phase LLM prompting and deterministic validation
achieves: IWSR\,=\,95\% (LLM-assisted), IWSR\,=\,100\% (deterministic),
SCR\,=\,SVR\,=\,100\% in both modes, SS\,=\,0.938, and zero payload
schema violations.
All residual LLM failures are service-routing errors on deliberately
ambiguous intents; no payload-level error occurs, validating the
effectiveness of the schema-grounded Phase\,2 mechanism.

The six reliability metrics (IWSR, SCR, SVR, HR, SS, RRF) constitute
a reusable, domain-specific evaluation framework applicable to any
intent-to-API orchestration system, regardless of LLM provider or
underlying telecom infrastructure.

Future work includes: cross-model reliability benchmarking (Gemini,
GPT-4o, open-weight models) to establish provider-agnostic bounds;
integration of 3GPP ZSM closed-loop control for fully autonomous
network management; user studies measuring the impact of intent
phrasing on translation reliability; extension of the evaluation
dataset with real operator intent logs; and exploration of fine-tuned
smaller models to reduce per-intent LLM cost while maintaining
reliability targets.

All source code, the ground-truth dataset, and evaluation scripts
are publicly available at:
\url{https://github.com/doadurak/mini-telco-platform}.
