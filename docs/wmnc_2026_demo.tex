\begin{abstract}
We demonstrate an open-source platform that converts free-text operator intents into
live CAMARA API calls. A two-phase large-language-model (LLM) planner selects the CAMARA
service and builds a schema-grounded payload, and a three-layer deterministic validator
(schema, telecom semantics, live CAPIF registry) gates every call. Quality of Service
(QoS) requests are authorized by the PCF of a containerized Open5GS 5G core with
UERANSIM-emulated UEs. A live request takes 2.2--4.8\,s with GPT-4o-mini or
Claude\,Haiku\,4.5 (6.9--8.2\,s with Gemini), of which LLM planning accounts for 78--99\%.
On 300 unique bilingual intents (three runs each), the LLM planners reach an
Intent-to-API Workflow Success Rate (IWSR) of 95.3--96.6\%, compared with 83.3\% for a
keyword baseline and 36.0\% for native function calling.
Code, testbed and data: \url{https://github.com/doadurak/mini-telco-platform}.
\end{abstract}

\section{Introduction}
Zero-touch Beyond-5G management requires orchestration layers that translate high-level
intents into standards-compliant API invocations~\cite{coronado2022}. 3GPP
CAPIF~\cite{3gpp_capif} and CAMARA~\cite{camara_project,camara2022} standardize how verticals
discover and consume network capabilities, but closing the intent-to-API gap on a
\emph{live} exposure stack remains open. OpenCAPIF~\cite{molina2022} provides exposure
infrastructure without NL planning; Turkovic~et~al.~\cite{turkovic2025} ran live CAMARA
QoD with hand-written payloads; Maatouk~et~al.~\cite{maatouk2025} identify hallucination
as the key risk of telecom LLMs, and Liu~et~al.~\cite{liu2024} report 40\% JSON-schema
compliance for ungrounded GPT-4. Our open platform combines live CAPIF onboarding,
schema-grounded multi-LLM planning, a three-layer validator, and CAMARA execution down
to a 3GPP PCF.

\section{Platform Architecture}
\label{sec:arch}
\begin{figure}[t]
  \centering
  \includegraphics[width=0.90\columnwidth]{fig1_architecture.pdf}
  \caption{Platform architecture. Any L1--L3 failure triggers at most three payload
  corrections; CAPIF-1e runs over mTLS, provider calls over HTTP.}
  \label{fig:arch}
\end{figure}
\textit{Planning:} A FastAPI backend exposes \texttt{POST\,/orchestrate}
(Fig.~\ref{fig:arch}). Phase\,1 selects one of four CAMARA services (QoD\,v1.1,
QoS\,Profiles, QoS\,Provisioning, Location\,Retrieval\,v0.5) from a schema-grounded
catalog; Phase\,2 generates the payload from the operation's OpenAPI schema, which is
injected into the prompt~\cite{flowmind2023}. Intent-level QoS classes (e.g.\
\texttt{QOS\_E\_STREAMING}) are mapped by target bit rate to the operator profiles the
network enforces (\texttt{QOS\_E/S/M/L}).

\textit{Validation:} L1 checks the payload against its Pydantic schema; L2 enforces
telecom rules (E.164 numbers, QoS profiles that map to an operator profile, durations of
1--7200\,s, unicast IPv4); L3 queries the live
CAPIF registry to confirm that the selected service is published. L1--L3 cannot detect a
registered but wrong service; therefore, a live plan whose service differs from the one
chosen by the keyword planner is held until the operator confirms it.

\textit{Execution:} For QoS, the adapter resolves the phone number to the UE's IP from
the 5GC subscriber database; the CAMARA provider forwards an AsSessionWithQoS
subscription to the NEF, which creates a PCF application session bound to the UE's PDU
session. Location uses the NEF Monitoring Event API with emulated core
data~\cite{plastras2026}. The CAMARA and NEF services are NCSRD's open-source
implementations~\cite{front_repos}.

\section{Live Demonstration}
\label{sec:demo}
\begin{figure}[t]
  \centering
  \includegraphics[width=0.50\columnwidth]{fig2_live_orchestrate.png}
  \caption{Recorded live response (S1, GPT-4o-mini, \texttt{dry\_run:false}, MSISDN masked).}
  \label{fig:ui}
\end{figure}
The full stack of Fig.~\ref{fig:arch}, including Open5GS~\cite{open5gs} and
UERANSIM~\cite{ueransim}, runs on one 16\,GB host via \texttt{start.sh}. All
scenarios run with \texttt{dry\_run:false}, and their responses are in the repository.
\textbf{S1 (QoD):} \textit{``Activate video-streaming quality for $\langle$MSISDN$\rangle$
for the next 30 minutes''} yields \texttt{QOS\_E\_STREAMING}, 1800\,s, enforced as
\texttt{QOS\_S}; the PCF accepts the session and QoD returns HTTP\,201,
\texttt{AVAILABLE} (Fig.~\ref{fig:ui}).
\textbf{S2 (Location):} the NEF returns a WGS-84 area (HTTP\,200).
\textbf{S3 (ambiguity):} dataset entry \textit{``Provide network quality improvement for
device $\langle$MSISDN$\rangle$ for a long time''} (ground truth: QoD). All three LLMs
select QoS\,Provisioning in every run, and the plan passes L1--L3; because the keyword
planner selects QoD, the cross-check holds the call until it is confirmed, after which
the PCF accepts it (\texttt{ACTIVE}).
\textbf{S4 (backend switch):} after each \texttt{POST\,/config/provider} switch, S1
yields identical CAMARA payloads from all three LLMs. UERANSIM lacks NGAP PDU Session Resource Modify, so the
dedicated QoS flow is authorized by the core but not enforced on the emulated radio.

The dataset holds 300 unique intents (152\,EN / 148\,TR; 96 easy, 94 medium, 110 hard):
275 across the four services and 25 ambiguous edge cases. We derived the ground truth
(service, operation, payload checks) from the CAMARA OpenAPI constraints and NEF test
fixtures; independent multi-annotator labelling, in particular of the 25 ambiguous
intents, is left for future work. IWSR is the share of plans that select the correct
service and pass validation; HR is the share of wrong service selections. Each LLM
planner ran three times (temperature 0.1) without provider calls; every plan targets a
published service, so L3 never rejects one. The keyword rules were written for a 60-intent
pilot (100\% there, 79.2\% on the other 240; LLMs 95.4--96.5\%). IWSR varies by at most
0.6 points across runs; the 10--14 failures per run are mostly QoD vs.\
QoS\,Provisioning confusions on hard intents (as in S3). Across the nine LLM runs, the
cross-check holds 75 of these 92 wrong selections before execution, at the cost of a
confirmation for 16\% of correct plans.
\textit{Native function calling} (one tool per CAMARA operation, OpenAPI schema as
parameters) selects services almost as well (HR 5.0\%) but omits required fields that
the intent does not state (e.g.\ \texttt{applicationServer}); our feedback loop repairs
181 such plans (2--3 per run for the two-phase planner).
\textit{Fault injection} (Table~\ref{tab:faults}): every fault is caught by its layer;
GPT-4o-mini feedback repairs L1/L2 faults in one iteration but cannot fix an unpublished
service. \textit{Scalability and LLM APIs:} with live L3, one backend process serves
$\approx$160\,req/s with the keyword planner; with GPT-4o-mini, latency stays at
$\approx$2.6\,s up to 10 concurrent requests, so the LLM API is the bottleneck. If it
fails, \texttt{auto} mode uses the keyword planner. As intents (with MSISDNs) reach an external API, production
use needs pseudonymization or a self-hosted model.
