\begin{abstract}
We demonstrate an open-source platform that converts free-text operator intents into
live CAMARA API calls. A two-phase large-language-model (LLM) planner selects the CAMARA
service and builds a schema-grounded payload, and a three-layer deterministic validator
(schema, telecom semantics, live CAPIF registry) gates every call. Quality of Service
(QoS) requests are authorized by the PCF of a containerized Open5GS 5G core with
UERANSIM-emulated UEs. A live request takes 2.2--4.8\,s with GPT-4o-mini or
Claude\,Haiku\,4.5 (6.9--8.2\,s with Gemini), of which LLM planning accounts for 78--99\%.
On 300 unique bilingual intents, the LLM planners reach an Intent-to-API Workflow Success
Rate (IWSR) of 95.3--97.3\%, compared with 83.3\% for a keyword baseline and 16.3\% for
GPT-4o-mini without schema grounding.
Code, testbed and data: \url{https://github.com/doadurak/mini-telco-platform}.
\end{abstract}

\section{Introduction}
Zero-touch Beyond-5G management requires orchestration layers that translate high-level
intents into standards-compliant API invocations~\cite{coronado2022}. 3GPP
CAPIF~\cite{3gpp_capif} and GSMA CAMARA~\cite{camara2022} standardize how verticals
discover and consume network capabilities, but closing the intent-to-API gap on a
\emph{live} exposure stack remains open. OpenCAPIF~\cite{molina2022} provides exposure
infrastructure without NL planning; Turkovic~et~al.~\cite{turkovic2025} ran live CAMARA
QoD with hand-written payloads; Maatouk~et~al.~\cite{maatouk2025} identify hallucination
as the key risk of telecom LLMs, and Liu~et~al.~\cite{liu2024} report 40\% JSON-schema
compliance for ungrounded GPT-4. Our open platform combines live CAPIF onboarding,
schema-grounded multi-LLM planning, a three-layer validator, and CAMARA execution down
to a 3GPP PCF.

\section{Platform Architecture}
\label{sec:arch}
\begin{figure}[t]
  \centering
  \includegraphics[width=0.96\columnwidth]{fig1_architecture.pdf}
  \caption{Platform architecture. Any L1--L3 failure triggers at most three payload
  corrections; CAPIF-1e runs over mTLS, provider calls over HTTP.}
  \label{fig:arch}
\end{figure}
\textit{Planning:} A FastAPI backend exposes \texttt{POST\,/orchestrate}
(Fig.~\ref{fig:arch}). Phase\,1 selects one of four CAMARA services (QoD\,v1.1,
QoS\,Profiles, QoS\,Provisioning, Location\,Retrieval\,v0.5) from a schema-grounded
catalog; Phase\,2 generates the payload from the operation's OpenAPI schema, which is
injected into the prompt~\cite{flowmind2023}. Intent-level QoS classes (e.g.\
\texttt{QOS\_E\_STREAMING}) are mapped by target bit rate to the operator profiles the
network enforces (\texttt{QOS\_E/S/M/L}).

\textit{Validation:} L1 checks the payload against its Pydantic schema; the share of
plans that pass L1 is the Schema Compliance Rate (SCR). L2 enforces telecom rules (E.164
numbers, QoS profiles that map to an operator profile, durations of 1--7200\,s, unicast
IPv4); the share that pass L2 is the Semantic Validity Rate (SVR). L3 queries the live
CAPIF registry to confirm that the selected service is published. If the planner selects
a registered but wrong service, L3 accepts it; such errors are only detected by comparison
with the ground truth (IWSR).

\textit{Execution:} For QoS, the adapter resolves the phone number to the UE's IP from
the 5GC subscriber database; the CAMARA provider forwards an AsSessionWithQoS
subscription to the NEF, which creates a PCF application session bound to the UE's PDU
session. Location uses the NEF Monitoring Event API with emulated core data.

\section{Live Demonstration}
\label{sec:demo}
\begin{figure}[t]
  \centering
  \includegraphics[width=0.74\columnwidth]{fig2_live_orchestrate.png}
  \caption{Recorded live response (S1, GPT-4o-mini, \texttt{dry\_run:false}), rendered
  from the stored JSON in the repository (MSISDN masked).}
  \label{fig:ui}
\end{figure}
The full stack of Fig.~\ref{fig:arch} runs on one 16\,GB host via \texttt{start.sh}. All
scenarios run with \texttt{dry\_run:false}, and their responses are in the repository.
\textbf{S1 (QoD):} \textit{``Activate video-streaming quality for $\langle$MSISDN$\rangle$
for the next 30 minutes''} yields \texttt{QOS\_E\_STREAMING}, 1800\,s, enforced as
\texttt{QOS\_S}; the PCF accepts the session and QoD returns HTTP\,201,
\texttt{AVAILABLE} (Fig.~\ref{fig:ui}).
\textbf{S2 (Location):} the NEF returns a WGS-84 area (HTTP\,200).
\textbf{S3 (ambiguity):} dataset entry \textit{``Provide network quality improvement for
device $\langle$MSISDN$\rangle$ for a long time''} (ground truth: QoD). In the offline
benchmark, GPT-4o-mini selected QoD, whereas Claude and Gemini selected QoS\,Provisioning;
in the recorded live run, all three selected QoS\,Provisioning, which the PCF accepted
(\texttt{ACTIVE}). Every plan passes L1--L3 and executes: the validator ensures that calls
are well-formed and target registered services, not that the service matches the intent.
\textbf{S4 (backend switch):} after each \texttt{POST\,/config/provider} switch, S1
yields identical CAMARA payloads from all three LLMs. UERANSIM lacks NGAP PDU Session Resource Modify, so the
dedicated QoS flow is authorized by the core but not enforced on the emulated radio.

The dataset holds 300 unique intents (152\,EN / 148\,TR; 96 easy, 94 medium, 110 hard):
275 across the four services and 25 ambiguous edge cases. We derived the ground truth
(service, operation, payload checks) from the CAMARA OpenAPI constraints and NEF test
fixtures; it supersedes a 60-entry pilot (\texttt{datasets/legacy\_pilot\_60/}).
IWSR is the share of plans that select the correct service and pass validation; HR is
the share of wrong service selections. SS is one minus the standard deviation of IWSR
across the three difficulty levels: it measures robustness to difficulty, not run-to-run
repeatability. Planning uses temperature 0.1, so choices on ambiguous intents can vary
between runs (cf.\ S3). The benchmark makes no provider calls; all 1,200 recorded plans
pass the live L3 check. The keyword rules were written for the 60 pilot intents, on which
the baseline scores 100\%; on the 240 held-out intents it drops to 79.2\%, while the LLMs
reach 95.4--97.1\%. The 8--14 failures per LLM are mostly confusions between QoD and
QoS\,Provisioning (as in S3), and most occur on hard intents (IWSR 87--95\%, versus
99--100\% on easy and medium intents).
\textit{Ablations:} without the operation's schema and field rules in Phase\,2,
GPT-4o-mini invents field names and its SCR falls to 16.7\% (cf.\ 40\% for ungrounded
GPT-4 in~\cite{liu2024}); without feedback, a single-call planner reaches an IWSR of
77.3\% and our two-phase planner 96.7\%.
\textit{Fault injection} (Table~\ref{tab:faults}): each fault is caught by its target
layer. Feedback repairs L1/L2 faults in one iteration but not an unpublished or
wrong-but-registered service, because it only rewrites the payload.
\textit{Scalability and LLM APIs:} without an LLM (keyword planner, live L3 checks), a
single backend process handles $\approx$160\,req/s (95th-percentile latency 156\,ms with
20 concurrent clients). With GPT-4o-mini, latency stays at $\approx$2.6\,s for up to 10
concurrent requests, and throughput grows linearly from 0.34 to 3.3\,req/s; hence the LLM
API, not the platform, is the bottleneck. If the LLM API fails, \texttt{auto} mode falls
back to the keyword planner. Because intents, including MSISDNs, are sent to an external
API, production use requires pseudonymization or a self-hosted model.
